### 🧩 1. What Is Microsoft Fabric?

Microsoft Fabric is a **unified SaaS analytics platform** that integrates **Data Factory, Synapse, Power BI, and OneLake** under one umbrella.
Think of it like this:

> “Azure + Power BI + Data Engineering tools = one seamless workspace.”

Fabric handles **data ingestion → storage → transformation → analytics → visualization** all in one place.

#### 🔹 Core Fabric Layers:

| Layer      | Tool                                                  | Role                          |
| ---------- | ----------------------------------------------------- | ----------------------------- |
| Ingestion  | **Dataflow Gen2**, **Pipeline**, **Notebook**         | Bring data in                 |
| Storage    | **Lakehouse**, **Warehouse**, **KQL DB**              | Store data                    |
| Modeling   | **Semantic Model (Power BI Dataset)**                 | Build relationships, measures |
| Analytics  | **Power BI Reports**, **Notebooks**                   | Insights & visualizations     |
| Governance | **Sensitivity Labels**, **Row/Object-level Security** | Control & compliance          |

## ⚙️ 2. Data Ingestion in Fabric (Q1–Q3 core concept)

Fabric offers **three main ways** to get data in. Each has its use case.

| Method                        | Type                     | Best For                               | Skills Needed    |
| ----------------------------- | ------------------------ | -------------------------------------- | ---------------- |
| **Dataflow Gen2**             | Low-code (Power Query M) | Small to medium data + transformations | Power Query M    |
| **Pipeline (Copy Activity)**  | Low-code orchestration   | Large-scale data ingestion             | Basic Fabric GUI |
| **Notebook (PySpark, Scala)** | Code-based               | Complex logic, ML, big data            | Python/Spark     |

💡 **Rule of Thumb:**

* If the **volume is large (GB/TB)** → use **Copy activity**
* If **you need transformation + cleaning** → use **Dataflow Gen2**
* If **you need custom logic / ML** → use **Notebook**

## 🪣 3. Data Storage Types in Fabric (Q4–Q7 concept)

Fabric offers multiple storage engines — choose based on *data type + query need*:

| Storage Type  | Data Type                      | Query Language       | Example Use                |
| ------------- | ------------------------------ | -------------------- | -------------------------- |
| **Lakehouse** | Structured + Semi/Unstructured | Spark, SQL           | Data engineering, big data |
| **Warehouse** | Structured (relational)        | T-SQL                | BI models, fact/dim tables |
| **KQL DB**    | Real-time/log data             | Kusto Query Language | Streaming / telemetry      |
| **Shortcut**  | Virtual link to existing data  | N/A                  | Reuse data without copying |

🧠 **Architectural Pattern Memory:**

* *Lakehouse = Data Engineer’s playground*
* *Warehouse = Analyst’s playground*
* *KQL DB = Real-time detective*

## 🧠 4. Dataflow Gen2 (Power Query Logic) — (Q4, Q5, Q14–Q18)

### What it is:

A **visual ETL tool** built on **Power Query M language**.
You use it for *low-code data transformation* before loading data into the lakehouse or warehouse.

### Key M Concepts:

* **Applied Steps** = transformation history
* **M Language** = functional, step-based (not SQL)
* **Table.Buffer** = freezes order / prevents recalculation
* **Query Folding** = keeps transformations executed at the source (faster)

### Common Applied Steps:

| Step           | Use                | Folding          |
| -------------- | ------------------ | ---------------- |
| Filter rows    | Limit data early   | ✅ Foldable       |
| Remove columns | Drop unnecessary   | ✅                |
| Add Index      | Add sequence       | ❌ breaks folding |
| Split Column   | Separate text/date | ❌ breaks folding |

💡 **Exam Pattern:**
If a question mentions *“improve performance”*, apply **filters before non-foldable transformations**.

## 📐 5. Schema Design & Joins (Q6–Q11 concept)

### 🌟 Star Schema

A **fact table** (numbers, measures) connected to **dimension tables** (descriptions).

| Table Type | Contains               | Example                |
| ---------- | ---------------------- | ---------------------- |
| Fact       | Numeric + foreign keys | SalesAmount, ProductID |
| Dimension  | Descriptive attributes | ProductName, Category  |

🧠 **Golden Rule:**
👉 *Fact = What Happened (measure)*
👉 *Dimension = What it’s About (context)*

### 💬 Joins (Power Query & SQL)

| Join Type       | Meaning               | When to Use         |
| --------------- | --------------------- | ------------------- |
| **Inner**       | Only matches          | Clean, matched data |
| **Left Outer**  | Keep all left         | Preserve main data  |
| **Left Anti**   | Keep left not matched | Exclusion logic     |
| **Right Outer** | Opposite of left      | Rarely used         |
| **Cross**       | Cartesian product     | Never in exam 😅    |

**Query Folding Tip:**
Joins are foldable, Anti joins often aren’t if not supported by the source.

## ⚡️ 6. SQL Logic Refresher (Q19–Q23 core)

Fabric Warehouse uses **T-SQL** syntax (same as Azure SQL).
You’ll often see questions about aggregation, filtering, and grouping.

### Key SQL Patterns:

| Goal                  | Example                       | Explanation                  |
| --------------------- | ----------------------------- | ---------------------------- |
| Aggregate by category | `SELECT Category, SUM(Sales)` | Summarize                    |
| Date filter           | `WHERE YEAR(Date)=2024`       | Works across all SQL sources |
| Latest per group      | `MAX(Date)` with `GROUP BY`   | Finds latest                 |
| Filter small stock    | `WHERE stock_quantity < 50`   | Simple filter                |

**Exam Tip:**
If you see *“latest record per category”*, always think:
`GROUP BY Category` + `MAX(DateColumn)`

## 🔐 7. Security & Compliance in Fabric (Q25–Q29 core)

| Feature                         | Purpose                      | Level          |
| ------------------------------- | ---------------------------- | -------------- |
| **Sensitivity Labels**          | Classify & protect data      | Metadata level |
| **Row-Level Security (RLS)**    | Filter data by user          | Data level     |
| **Object-Level Security (OLS)** | Hide specific tables/columns | Model level    |
| **Workspace Roles**             | Manage access in workspace   | User level     |
| **Dynamic Data Masking**        | Obfuscate sensitive info     | SQL engine     |

💡 **Pattern to Remember:**
🧱 Security in Fabric =
“**Label + Limit + Mask**”
→ Label = sensitivity, Limit = RLS/OLS, Mask = DDM.

## 🔁 8. Deployment Pipelines & Versioning (Q30–Q36)

Fabric has **Deployment Pipelines** to manage Dev → Test → Prod.

### 🔹 Why:

To prevent inconsistency between environments.

### 🔹 Key Terms:

| Term                 | Meaning                                  |
| -------------------- | ---------------------------------------- |
| **Deployment Rules** | Customize parameters per stage           |
| **Autobinding**      | Maintains links between models & reports |
| **Related Items**    | Deploy datasets & reports together       |
| **XMLA Endpoint**    | Advanced API access for semantic models  |

🧠 **Remember:**

* XMLA = no PBIX download.
* Autobinding = keep relationships intact.
* Parameter Rule = filter or limit data for dev/test.

## 💾 9. Performance Optimization (Q37–Q47)

### a) DAX & Virtual Relationships

* **TREATAS()** → Creates *virtual filter relationships* between tables.
* **USERELATIONSHIP()** → Activates an existing inactive relationship.

### b) Large Semantic Models

* For models >10 GB → enable **Large semantic model storage format**.
* F64 capacity or higher required.

### c) Aggregations

* Create smaller **pre-aggregated tables** for speed.
* Test with **DAX Studio** and **SQL Profiler** → detect *cache hit or miss*.

### d) Query Performance

* Use **Performance Analyzer** (Power BI Desktop) to find slow visuals.
* Use **Best Practice Analyzer** (Tabular Editor) for model health.

## 🧮 10. Lakehouse Optimization & Notebooks (Q47–Q50)

### ⚙️ OPTIMIZE + VACUUM Commands

* **OPTIMIZE** → Combine small Parquet files into larger ones → improves query speed.
* **VACUUM** → Delete old unused files → reduce storage.

💡 Ideal File Size = **128 MB–1 GB**

### 🧩 High Concurrency Sessions

* Found under **Workspace settings**, not Notebook or Tenant level.
* Needed when many users run notebooks simultaneously.

### 🕒 Incremental Refresh Parameters

* Use **RangeStart** and **RangeEnd** (case-sensitive).
* Filters data for refresh windows — essential for large datasets.
